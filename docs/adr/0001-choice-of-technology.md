# ADR-001: Вибір архітектури сховища даних для часових рядів телеметрії та діагностичних подій

* **Статус:** Approved  
* **Дата:** 2026-11-10  
* **Автор:** Дмитро Горинюк (Lead Software Engineer)  
* **Технічний контекст:** Розділ 2 (Архітектура проєкту), трасування до вимог [SRS-FUN-02](../srs.md#2-functional-requirements-функціональні-вимоги) та [SRS-NFR-PERF-01](../srs.md#3-non-functional-requirements-матриця-нефункціональних-вимог)

## 1. Context (Контекст та постановка проблеми)
Платформа моніторингу технічного стану транспортних засобів обробляє два принципово різних типи інформаційних потоків:
1. **Реляційні сутності бізнес-домену:** профілі користувачів, права доступу (RBAC), прив'язки автомобілів (VIN-коди, комплектація, історія регламентних робіт, довідники кодів помилок DTC за стандартом SAE J2012). Дані вимагають суворої транзакційної цілісності (ACID) та складних реляційних зв'язків.
2. **Високоінтенсивні часові ряди сенсорів (Time-series data):** безперервні виміри частоти обертання колінчастого валу (RPM), температури мастила, тиску наддуву, короткострокових/довгострокових паливних корекцій, що надходять з частотою до 10–20 Гц на активне авто при цільовому піковому навантаженні сервісу $\ge 500$ RPS.

Виникла дилема: використання чистої документоорієнтованої NoSQL-бази даних (MongoDB) для всього проєкту проти гібридного використання TimescaleDB (розширення для часових рядів поверх реляційного PostgreSQL).

---

## 2. Alternatives Considered (Розглянуті альтернативи)

### Альтернатива 1: MongoDB (Документоорієнтована NoSQL СУБД)
* **Переваги:** Гнучка схема документів (Schema-less), що дозволяє зберігати довільний набір параметрів з різних марок авто без міграцій; простота горизонтального шардингу "з коробки".
* **Недоліки (станом на 2026 рік):** 
  * Відсутність нативної оптимізації стиснення колоночного типу для строго циклічних часових рядів (високі FinOps-витрати на RAM та дисковий простір NVMe).
  * Обмежена підтримка складних аналітичних віконних функцій (`time_bucket`, рухоме середнє, інтерполяція пропусків сенсорів) порівняно зі стандартом SQL:2016.
  * Ризик деградації консистентності транзакцій при зв'язуванні історії ремонту авто та параметрів телеметрії без суворих Foreign Keys.

### Альтернатива 2: PostgreSQL з розширенням TimescaleDB (Обраний варіант)
* **Переваги:**
  * Автоматичне партиціювання таблиць на чанки за часом та VIN-кодом через абстракцію **Hypertables**.
  * Нативне гібридне колоночне стиснення даних часових рядів (алгоритми Gorilla та Delta-of-delta), що зменшує обсяг сховища на **85–90%** порівняно зі звичайними рядковими таблицями.
  * Єдине середовище виконання: строгий ACID та Foreign Keys для сутностей користувачів і авто поруч із надшвидкою аналітикою часових рядів за допомогою єдиного SQL-інтерфейсу.
* **Недоліки:**
  * Вертикальне масштабування окремого вузла запису (складніше налаштування мультивузлового кластера TimescaleDB порівняно з MongoDB Sharded Cluster).
  * Вищі вимоги до попереднього проєктування схеми даних (Schema Migrations через Alembic).

---

## 3. Decision (Прийняте рішення)
Затвердити **PostgreSQL з активованим розширенням TimescaleDB** як основне та єдине сховище для реляційних даних і телематичних часових рядів.

### Інженерне обґрунтування:
1. **Зниження архітектурної складності:** Відпадає необхідність підтримки патерну Polyglot Persistence (двох різних СУБД — наприклад, PostgreSQL для бізнес-сутностей + MongoDB/InfluxDB для телеметрії), що зменшує експлуатаційні витрати на резервне копіювання, моніторинг та синхронізацію транзакцій.
2. **Висока продуктивність агрегацій:** Вбудована функція `time_bucket()` та механізм Continuous Aggregates дозволяють будувати готові погодинні/добові зрізи деградації датчиків авто у фоновому режимі без навантаження на основний потік інференсу ML.
3. **Дотримання вимог надійності:** Повна підтримка транзакційного механізму WAL та реплікації для критичних діагностичних записів.

---

## 4. Consequences (Наслідки та компроміси)

### Позитивні наслідки:
* Забезпечено гарантовану пропускну здатність вставки пакетів телеметрії понад 10 000 метрик/сек на одиничний вузол за рахунок батч-запису в окремі чанки пам'яті.
* Скорочення витрат на сховище на $\approx 85\%$ завдяки нативній компресії старих чанків ($> 7$ діб).
* Уніфікація стеку ORM: використання SQLAlchemy 2.0 (Async) для всіх доменних шарів без необхідності підключення додаткових клієнтів ODM.

### Негативні наслідки та ризики (Trade-offs):
* **Ризик розростання індексів (Index Bloat):** При некоректному налаштуванні часового інтервалу чанків (`chunk_time_interval`) розмір B-Tree індексів може перевищити обсяг оперативної пам'яті (`shared_buffers`).
  * *Мітигація:* Встановити інтервал партиціювання чанків рівним 24 годинам і впровадити автоматичну політику архівації чанків старіших за 30 днів.
* **Складність горизонтального скейлінгу на запис:** При перевищенні ліміту в 10 000 RPS на вставку виникне потреба у переході на TimescaleDB Distributed Hypertables або винесенні прийому даних у брокер повідомлень (RabbitMQ / Kafka).
  * *Мітигація:* Архітектура системи вже передбачає буферизацію через RabbitMQ на Рівні 2 C4 Model.
