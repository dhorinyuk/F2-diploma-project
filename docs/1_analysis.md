# Інженерний опис аналогів

## 1. Car Scanner ELM OBD2 (Мобільна та хмарна телеметрична система)
- **Архітектурний патерн:** Монолітна клієнт-серверна архітектура з локальним збереженням даних на пристрої та хмарною синхронізацією. Викликає обмеження при горизонтальному масштабуванні та обробці масивів історичних даних великих автомобільних парків.
- **Протоколи передачі даних:** Синхронні HTTP/REST API для синхронізації з хмарою, Bluetooth/Wi-Fi (ELM327 протокол) для збору даних з OBD-II адаптерів.
- **Базовий стек даних:** Локальна SQLite на клієнті, реляційні бази даних у хмарному сховищі. Консистентність забезпечується транзакційними механізмами СУБД без розподілених блокувань.
- **Критичні інженерні недоліки (Technical Bottlenecks):** Відсутність надійного брокера повідомлень для асинхронної обробки великих потоків телеметрії, висока латентність (Latency) при пакетному завантаженні логів, відсутність вбудованих ML-модулів прогнозування несправностей у реальному часі.

## 2. Fleetio (Платформа управління техобслуговуванням і телеметрією)
- **Архітектурний патерн:** Розподілена сервісна архітектура з виділеними мікросервісами для інвойсингу, телеметрії та управлінських звітів. Забезпечує високу масштабованість, проте має високу складність конфігурації.
- **Протоколи передачі даних:** REST API, Webhooks для сповіщень, MQTT для інтеграції з IoT-трекерами транспортних засобів.
- **Базовий стек даних:** PostgreSQL як основне реляційне сховище, Redis для кешування сесій та черг. Використовується модель Eventual Consistency для розподілених подій.
- **Критичні інженерні недоліки (Technical Bottlenecks):** Висока вартість хмарної інфраструктури (FinOps-проблематика), складність підтримання консистентності даних при збоях у мережі IoT-пристроїв, залежність від сторонніх хмарних провайдерів.

## 3. Openmatics (Модульна телеметрична IoT-платформа)
- **Архітектурний патерн:** Подієво-керована архітектура (Event-Driven Architecture) з використанням шини даних для обробки потоків датчиків.
- **Протоколи передачі даних:** MQTT, AMQP та REST API для взаємодії компонентів.
- **Базовий стек даних:** Time-series бази даних для телеметрії та реляційні сховища для метаданих.
- **Критичні інженерні недоліки (Technical Bottlenecks):** Високий поріг входження при розгортанні, складність діагностики помилок в асинхронних ланцюжках подій, обмежені можливості кастомного аналізу аномалій.

## Порівняльна інженерна матриця

| Критерій порівняння | Мій проєкт (FastAPI + RabbitMQ) | Car Scanner | Fleetio | Openmatics |
| :--- | :--- | :--- | :--- | :--- |
| **Тип архітектури** | Розподілена сервісна (EDA + REST) | Моноліт / Клієнт-хмара | Мікросервісна | Подієво-керована (EDA) |
| **Протоколи (API)** | REST API, AMQP (RabbitMQ) | REST API, Bluetooth (ELM327) | REST API, Webhooks, MQTT | MQTT, AMQP, REST API |
| **Бази даних (СУБД)** | PostgreSQL, Redis | SQLite, Реляційна хмарна СУБД | PostgreSQL, Redis | Time-series, Реляційна СУБД |
| **Швидкодія (Latency)** | Низька (асинхронна черга RabbitMQ) | Висока при пакетній синхронізації | Середня | Низька |
| **Відмовостійкість** | Висока (Retry, Idempotency, EDA) | Низька (залежність від прямого зв'язку) | Висока (кластеризація) | Висока (подієва шина) |
| **Аналітика / ML** | Вбудований ML-модуль (scikit-learn) | Відсутній / Базові коди DTC | Статистичні звіти | Базові правила тригерів |

## Аналітичний висновок підрозділу 1.2
Проведений інженерний аналіз існуючих аналогів (Car Scanner, Fleetio, Openmatics) засвідчив наявність суттєвих архітектурних обмежень у традиційних рішеннях. Зокрема, використання монолітних підходів та синхронних протоколів у Car Scanner призводить до критичних затримок (Latency) при обробці масивів телеметричних даних та унеможливлює реалізацію проактивного прогнозування несправностей. Водночас комерційні платформи на кшталт Fleetio мають надмірну складність і високу вартість розгортання, що обмежує їхнє локальне застосування.

Для усунення виявлених недоліків у межах кваліфікаційної роботи обрано гетерогенний стек на базі Python (FastAPI), брокера повідомлень RabbitMQ та реляційного сховища PostgreSQL. Застосування подієво-керованої архітектури (Event-Driven Architecture) та асинхронної обробки подій забезпечує ізоляцію сервісів збору телеметрії та аналітичного модулю, гарантуючи високу відмовостійкість (Fault Tolerance) і масштабованість системи. Інтеграція алгоритмів машинного навчання (scikit-learn) дозволяє здійснювати автоматизоване виявлення аномалій безпосередньо в конвеєрі обробки даних, що вирішує проблеми статичної діагностики, притаманної більшості аналогів.

## 1.5. Формалізація вимог та модель To-Be
- **Концептуальна модель To-Be:** Розгортання розподіленої вебплатформи з асинхронним брокером повідомлень RabbitMQ для забезпечення проактивного виявлення несправностей без блокування клієнтського інтерфейсу.
- **Функціональні вимоги (Core Features):**
  1. Модуль управління профілями та метаданими транспортних засобів.
  2. Сервіс приймання, валідації та нормалізації вхідної телеметрії.
  3. Брокер подій (RabbitMQ) для асинхронної маршрутизації подій.
  4. Аналітично-діагностичний модуль на базі scikit-learn для пошуку аномалій.
  5. Модуль прогнозування ризиків відмови вузлів авто.
  6. Інтерфейсна панель (Dashboard) на React/TypeScript.
  7. Підсистема логування історії техобслуговування (ТО).
- **Нефункціональні вимоги (NFRs):**
  - **Продуктивність:** Пропускна здатність API $\ge$ 500 RPS; затримка (Latency) на p95 < 200 мс.
  - **Безпека:** OAuth 2.0 / OIDC із використанням JWT-токенів; шифрування TLS 1.3.
  - **Інфраструктура:** PostgreSQL з реплікацією, контейнеризація Docker.
