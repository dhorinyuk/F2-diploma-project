# Thesis Proposal

# 1. Попередня назва кваліфікаційного проєкту

**Українською:**

Розробка інтелектуальної вебплатформи аналізу технічного стану та прогнозування несправностей автомобілів

**English:**

Development of an Intelligent Web Platform for Vehicle Condition Analysis and Failure Prediction

---

# 2. Актуальність та проблематика

Сучасні автомобілі генерують значний обсяг діагностичних і телеметричних даних, що характеризують параметри роботи силової установки, трансмісії та інших систем транспортного засобу. Традиційні засоби діагностики переважно орієнтовані на виявлення зареєстрованих кодів несправностей і не забезпечують комплексного аналізу історичних даних, виявлення аномальних змін параметрів та оцінювання ризику виникнення потенційних технічних проблем.

Проблема полягає у відсутності єдиного програмного середовища, яке поєднує централізоване зберігання діагностичних даних, аналіз параметрів у часовій динаміці, автоматизоване виявлення аномалій та прогнозування потенційних несправностей.

Інженерна складність задачі визначається необхідністю побудови розподіленої програмної системи, організації синхронної та асинхронної взаємодії між компонентами, обробки структурованих телеметричних даних, збереження історії експлуатації, інтеграції алгоритмів машинного навчання, забезпечення безпеки API, автоматизованого тестування та контролю експлуатаційного стану системи.

---

# 3. Ідея програмного продукту

Пропонується розробити вебплатформу для централізованого збору, зберігання та інтелектуального аналізу діагностичних і телеметричних даних автомобілів.

Користувач зможе створювати профіль автомобіля, завантажувати або передавати діагностичні дані, переглядати історію параметрів, отримувати результати діагностичного аналізу, інформацію про виявлені аномалії та прогнозні оцінки потенційних технічних проблем.

Дані можуть надходити через програмний API або у вигляді підготовлених наборів даних. Архітектура системи передбачає можливість подальшого підключення зовнішнього OBD-II джерела без зміни основної логіки платформи.

---

# 4. Архітектура системи

## 4.1. Тип системи

Вебплатформа з розподіленою сервісною архітектурою, асинхронною обробкою даних та інтелектуальним аналізом телеметричної інформації.

## 4.2. Архітектурний підхід

Основою системи є сервісна архітектура з використанням:

- REST API для синхронної взаємодії;
- Event-Driven Architecture для асинхронної обробки телеметричних і діагностичних подій;
- окремого аналітичного/ML-компонента;
- реляційного сховища PostgreSQL;
- Redis для кешування та тимчасових даних;
- RabbitMQ як брокера повідомлень.

Основні програмні компоненти:

1. **Web Client** — користувацький вебінтерфейс.
2. **API Service** — автентифікація, авторизація та обробка HTTP-запитів.
3. **Vehicle Service** — керування профілями автомобілів.
4. **Telemetry Service** — приймання, валідація та збереження телеметричних даних.
5. **Diagnostic Service** — обробка діагностичних кодів та пов'язаних параметрів.
6. **Analytics/ML Service** — виявлення аномалій та прогнозування ризику несправностей.
7. **Notification Service** — формування та передавання повідомлень користувачу.

Для підвищення надійності асинхронної обробки передбачається використання retry-механізмів, idempotent-обробки повідомлень та контролю помилок обробки.

---

# 5. Core Features

## 1. Керування профілями автомобілів

Створення, редагування та зберігання профілів автомобілів із параметрами транспортного засобу та зв'язком з історією діагностичних і телеметричних даних.

## 2. Збір та зберігання телеметричних даних

Приймання діагностичних параметрів через API або завантаження підготовлених наборів даних, їх валідація, нормалізація та збереження для подальшого аналізу.

## 3. Діагностичний аналіз

Обробка кодів несправностей і пов'язаних параметрів із формуванням структурованого результату діагностики та прив'язкою результатів до конкретного автомобіля.

## 4. Виявлення аномалій

Автоматичне виявлення нетипових значень і відхилень у телеметричних даних із використанням статистичних методів та алгоритмів машинного навчання.

## 5. Прогнозування потенційних несправностей

Формування прогнозної оцінки ризику технічних проблем на основі історичних даних, характеристик експлуатації та результатів попереднього аналізу.

## 6. Аналітична панель

Візуалізація поточних та історичних параметрів автомобіля, результатів діагностики, виявлених аномалій і прогнозних показників у вебінтерфейсі.

## 7. Історія технічного обслуговування та сповіщення

Збереження інформації про виконані роботи з технічного обслуговування та формування сповіщень на основі заданих умов і результатів аналітичного модуля.

---

# 6. Інженерні вимоги та забезпечення якості

Система повинна забезпечувати:

- модульний розподіл програмних компонентів;
- валідацію вхідних даних;
- автентифікацію та авторизацію користувачів;
- контроль доступу до даних автомобілів;
- централізоване конфігураційне керування;
- обробку помилок і повторні спроби для асинхронних операцій;
- idempotent-обробку повідомлень;
- автоматизоване unit та integration/API тестування;
- статичний аналіз програмного коду;
- автоматизовану перевірку у CI/CD;
- контейнеризоване розгортання;
- моніторинг основних системних метрик;
- централізоване логування.

# 7. Попередній технологічний стек

## 7.1. Мови програмування

- **Python** — backend, обробка даних та ML-компонент.
- **TypeScript** — frontend.
- **SQL** — робота з реляційними даними.

## 7.2. Архітектурні патерни та підходи

- REST API.
- Event-Driven Architecture.
- Service-Oriented / Microservice Architecture.
- Layered Architecture.
- Repository Pattern.
- Асинхронна взаємодія між компонентами.
- Idempotent message processing.

## 7.3. Frameworks та бібліотеки

- **FastAPI** — backend API.
- **React** — вебінтерфейс.
- **SQLAlchemy** — ORM.
- **scikit-learn** — алгоритми машинного навчання та виявлення аномалій.

## 7.4. Бази даних та сховища

- **PostgreSQL** — основне реляційне сховище.
- **Redis** — кешування та тимчасові дані.

## 7.5. Message Broker

- **RabbitMQ** — асинхронна передача подій між програмними компонентами.

## 7.6. DevOps та інфраструктура

- **Git** — контроль версій.
- **GitHub** — хостинг репозиторію.
- **GitHub Actions** — CI/CD.
- **Docker** — контейнеризація.
- **Docker Compose** — локальне оркестрування компонентів.

## 7.7. Testing та Code Quality

- **Pytest** — автоматизоване тестування backend.
- **Ruff** — статичний аналіз та контроль якості Python-коду.

## 7.8. Observability

- **Prometheus** — збір системних метрик.
- **Grafana** — візуалізація та аналіз метрик.

## 7.9. Документація та архітектурний контроль

- **OpenAPI / Swagger** — документування та тестування REST API.
- **C4 Model** — опис архітектури системи.
- **ADR** — фіксація ключових архітектурних рішень.

---

# 8. DevSecOps та процес розробки

Процес розробки передбачає використання GitHub Actions для автоматизованого виконання тестів, статичного аналізу та перевірки основних програмних компонентів.

Для контейнеризованого середовища передбачається контроль конфігурації та перевірка залежностей і контейнерних компонентів на наявність відомих вразливостей.

Розробка програмного забезпечення повинна виконуватися з використанням версійного контролю, автоматизованих перевірок та документації архітектурних рішень.

---

# 9. Observability та надійність

Для контролю експлуатаційного стану системи передбачається збір основних метрик програмних компонентів та їх візуалізація.

Система повинна забезпечувати контроль помилок обробки повідомлень, повторні спроби виконання операцій та захист від повторної обробки однакових подій.

Такі механізми повинні забезпечувати контрольовану поведінку системи під час тимчасових збоїв та підвищувати надійність асинхронної взаємодії.

---

# 10. Очікуваний технічний результат

Результатом роботи має бути програмний прототип вебплатформи, здатний централізовано приймати, зберігати та аналізувати діагностичні й телеметричні дані автомобілів.

Система повинна забезпечувати:

- керування профілями автомобілів;
- приймання та зберігання телеметричних даних;
- діагностичний аналіз;
- виявлення аномальних значень;
- формування прогнозних оцінок ризику несправностей;
- візуалізацію результатів;
- збереження історії технічного обслуговування;
- асинхронну обробку даних;
- автоматизоване тестування та CI/CD;
- контроль якості програмного коду;
- моніторинг експлуатаційних метрик.

Архітектура системи повинна забезпечувати модульність, тестованість, можливість масштабування окремих компонентів, надійну асинхронну взаємодію та контроль експлуатаційного стану програмного середовища.

---

# 11. Напрями подальшої реалізації

Подальша реалізація кваліфікаційного проєкту передбачає послідовне проходження етапів системного проєктування, реалізації програмних компонентів, тестування, контейнеризації, автоматизації CI/CD та впровадження засобів observability.

Основними артефактами проєкту мають бути програмний код, архітектурна документація, автоматизовані тести, конфігурація контейнеризованого середовища та документація API.
